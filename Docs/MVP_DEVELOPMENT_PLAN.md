# MVP 制作阶段计划

状态：执行基线 v1.0

## 1. 阶段目标

本阶段从需求基线 `requirements-v1.0.0` 出发，先验证单人维修核心，再逐步加入联机和 MVP 系统。不得跳过前一阶段的可运行门禁批量开发后续功能。

首个 MVP 是一段约 30–45 分钟、能够代表最终游戏结构的完整体验；完整 4 小时以上主线属于 MVP 验证后的内容扩展，不在本阶段一次性生产。

## 2. 小阶段与门禁

| 阶段 | 当前要回答的问题 | 主要交付 | 可运行门禁 |
| --- | --- | --- | --- |
| M0 技术准备 | 工程能否稳定开发、测试和构建？ | Unity/渲染/输入/测试决策，程序集与目录，空场景测试构建 | 命令行或编辑器测试通过，空开发构建可启动 |
| M1 单机核心灰盒 | 维修本身是否清晰、有反馈？ | 冷却舱、第一人称、上下文交互、扳手、喷枪、管件和固定事故链 | 完整成功、失败、重置；自动测试通过 |
| M2 灰盒玩法评审 | 未读需求的玩家能否理解并愿意继续？ | 至少 3 份首次试玩记录和继续/修改/停止结论 | 满足 `GRAYBOX_SCOPE.md` 玩法退出条件 |
| M3 双人网络切片 | 核心劳动在延迟下是否仍成立？ | 监听主机、双进程、移动、共享物品、一条故障链、退出清理 | 两个真实进程在模拟网络条件下完成任务 |
| M4 2–4 人功能 MVP | 需求中的必要系统能否形成完整一局？ | 大厅、文字聊天、第三工具、协作、有限敌人、倒地救援、资源、结算和最小成长 | 2–4 人完成准备—远征—结算—重开 |
| M5 代表章节 | 玩法、低模表现和内容生产能否共同成立？ | 30–45 分钟代表章节、受控变化、基础美术、存档和设置 | 无开发者主持完成一局；性能与内容门禁通过 |
| M6 可分享 MVP | 好友能否独立安装、游玩和反馈？ | Windows 构建、说明、回归清单、已知问题、标签与 Bundle | 干净环境安装/连接/完成/退出均通过 |

## 3. M0 技术准备（已完成）

必须完成：

1. 确认可调用的 Unity 编辑器；M0 最初使用 `6000.0.38f1`，后由 ADR-0004 升级到 `6000.0.82f1`；
2. 决定 Built-in 或 URP，并记录 ADR；
3. 固定 Input System 和 Test Framework 用法；
4. 建立 Runtime、Content、Scenes、Tests/EditMode 和 Tests/PlayMode 程序集边界；
5. 建立最小启动场景、测试入口和命令行测试脚本；
6. 运行一次 EditMode、一次 PlayMode 和一次开发构建；
7. 记录结果、人工审查入口与已知限制。

M0 不安装网络框架、不制作玩法系统、不引入第三方美术包。

完成证据：Unity 命令行初始化成功，EditMode 3/3、PlayMode 1/1 通过，Windows x64 Development Build 已生成并完成真实播放器启动冒烟检查。下一阶段为 M1 单机核心灰盒。

## 4. 功能交付与人工审查格式

每次功能交付必须向项目推动者提供：

1. **本次实现**：用玩家能观察到的行为概括结果；
2. **代码地图**：列出新增/修改文件、核心类型和各自职责；
3. **运行路径**：从哪个场景或构建进入，按什么步骤操作；
4. **预期结果**：成功、失败、边界情况分别应看到什么；
5. **自动验证**：运行了哪些 EditMode、PlayMode、构建或脚本检查；
6. **已知限制**：占位内容、未实现项和技术债；
7. **需要人工操作**：明确写“无需”或给出逐步 Unity/建模/代码微调操作；
8. **版本位置**：分支、提交和是否已推送。

用户人工审查反馈优先记录观察事实，例如“准星指向阀门时显示了两个动作”，再记录改进建议。功能没有运行证据时不标记完成。

业务代码必须遵循 `ARCHITECTURE.md` 的注释规范。每次代码地图应优先指出核心入口、状态模型和关键设计注释，方便项目推动者进行人工检索与审查。

## 5. 可运行检查节奏

- 纯规则完成：立即运行 EditMode 测试；
- Unity 适配或场景交互完成：立即运行 PlayMode 测试；
- 普通玩家可见功能闭环：自动测试通过后，在 Unity 编辑器中执行人工运行检查；
- 一个完整事故链、网络切片或阶段候选完成：生成并启动开发构建；
- 一个小阶段完成：执行完整自动检查、人工运行清单、Git 提交和推送；
- 里程碑完成：创建版本标签与离线 Git Bundle。

如果本机无法调用正确 Unity 编辑器，允许继续编写计划和纯文本，但不得声称 C#、场景或构建已经通过运行验证。

## 6. 用户可能需要的人工工作

默认不要求用户手写业务代码或手工建模。我会优先完成可自动化的代码、灰盒、配置和测试。

可能需要用户参与：

- 首次在 Unity Hub 中安装或定位指定编辑器；
- 在 Unity 编辑器中确认画面、输入和手感；
- 参与首次玩家试玩并提供观察；
- 对无法通过命令行判断的场景布局进行主观确认；
- 后续学习简单模块化建模时，按单个资产的小步骤操作。

每次需要时必须说明目的、具体步骤、预期结果、失败截图/日志位置和是否阻塞后续工作。未明确提出时，用户无需主动修改代码或资产。

## 7. 版本策略

- 当前开发分支：`prototype/graybox`；
- 每个可运行闭环至少一个独立提交；
- M1 灰盒通过后创建 `prototype-v0.1.0` 标签和 Bundle；
- M3 网络切片通过后创建 `network-slice-v0.1.0`；
- M6 可分享版本创建 `mvp-v0.1.0`；
- 未通过门禁的实验不合并到 `main`。
