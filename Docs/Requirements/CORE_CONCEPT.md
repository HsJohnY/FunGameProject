# 核心游戏概念：巨构维修队

状态：需求基线 v1.0

## 一句话玩法

2–4 名维修员生活在一台穿越灾变区域的巨型移动机器上；玩家必须在机器持续前进时诊断连锁故障、协作搬运与安装零件、执行危险的舱外维修，并决定是否冒险停靠高危区域获取继续前进所需的资源。

## 玩家身份

玩家是共同负责一座移动巨构的维修队成员。团队不采用不可替换的固定职业；玩家可以根据当前故障、工具和位置形成临时分工。

巨构既是：

- 玩家共同维护的核心任务对象；
- 每局开始和结束的基地；
- 承载房间准备、设备配置和成长展示的空间；
- 将多个远征区域串联起来的共同资产。

巨构已确定为穿越风暴荒原的模块化多履带陆行工程平台和移动城镇。详见 `WORLD_THEME.md` 与 `CONTENT_AND_ART.md`。

## 不同人数的适配原则

### 已确认原则

- 所有玩家共享完成主线所需的基础维修能力。
- 不采用“缺少某个固定职业就无法完成任务”的硬职业门槛。
- 专业化应提供不同解法、资源效率或风险控制能力，而不是只修改进度条速度。
- 两人必须能完成主路径；三至四人获得更强的并行处理和可选目标能力。
- 人数更多时优先增加同时决策、信息分散和额外收益，不简单增加故障数量或数值。
- 玩家掉线后，会话应能降级继续或明确结束，不应因职业缺失永久卡死。

### 专业化后续边界

MVP 不实现专业认证、职业树或固定岗位，只由三种可自由更换和重复携带的工具形成临时分工。

“基础能力共享 + 专业工具包/认证”保留为首个可玩版本后的候选。若重新评审，专业必须提供替代解法、信息或风险控制，不能制造主线硬门槛或只修改进度条速度。

## 核心劳动

核心劳动由五类可组合动作构成：

1. **诊断**：根据仪表、声音、视觉症状和系统关系定位故障原因。
2. **拆装**：解除固定、拆除损坏模块、安装替换件。
3. **搬运**：单人或多人运输不同尺寸、重量和危险性的零件。
4. **连接**：重新连接电力、冷却、压力、信号或机械传动路径。
5. **校准与临时修复**：多人同步操作，或在资源不足时采取有副作用的应急方案。

这些动作必须发生在 3D 空间中，不得主要退化为菜单选项或独立 UI 小游戏。

## 核心体验承诺

- 玩家能理解机器为什么出现问题，而不是被纯随机故障惩罚。
- 同一故障允许不同处理顺序、工具组合或临时方案。
- 多个系统可能竞争临时资源，促使团队协调维修顺序，但熟练队伍应有机会完整解决主要问题。
- 舱内诊断、舱外执行、驾驶/资源调度形成信息与空间互补。
- 失误会造成连锁问题，但通常留有补救或降级运行方案。
- 团队维护的是共同资产，成功与失败都能在机器状态上被看见。

## 基础单局幻想

1. 队伍选择路线、任务、备件和工具。
2. 巨构进入危险区域并持续前进。
3. 环境压力和机器负载触发可解释的系统故障。
4. 玩家诊断问题、分配资源并执行维修。
5. 路线上出现补给点、捷径、可选任务或高风险停靠点。
6. 团队协调处理顺序和应急旁路，并可选择承担少量额外目标。
7. 抵达安全站、任务终点，或因核心系统彻底失效而结束。
8. 根据机器状态、任务成果和额外目标进行结算与配置调整。

完整单局阶段、失败、结算和安全站规则见 `RUN_AND_CAMPAIGN_STRUCTURE.md`。

## 游戏驱动力与里程碑

### 已确认的四层目标结构

1. **即时目标**：恢复一个系统、阻止故障恶化或救援队友。
2. **单局目标**：完成一次有意义的航程或任务，并结算成果、机器状态和损失。
3. **章节里程碑**：普通远征最终通向一次高强度阶段挑战，提供明确胜利节点。
4. **长期目标**：巨构在功能、空间或外观上产生可见变化，记录团队成果。

### 已确认章节结构

采用三章远征战役，每章围绕一座稳定站，由若干普通航程通向一次包含精英威胁的“工程灾难关”；最终进入中央区域并完成与校准核心结合的 Boss 战。

普通航程数量与少量路线变化在代表章节试玩后按内容产能决定，不属于 MVP 内容承诺。

## 需求收敛规则

本文的候选故障、系统、专业、路线和章节例子用于解释设计空间，不等于功能清单。进入开发前必须：

- 每个核心机制只保留一个明确方案，或明确写入原型对照测试；
- 将 MVP、后续版本和明确不做分开；
- 删除不服务三个最终体验支柱的功能；
- 为所有 MUST 需求提供可观察验收条件；
- 让首个灰盒只验证最关键的一条玩法假设。

## 合作必要性

- 舱外维修员依赖舱内玩家锁定机械、调节功率或提供状态信息。
- 大型零件需要多人搬运、固定和安装。
- 某些系统必须在不同位置同步校准。
- 多个故障同时发生时，团队需要分工、沟通和确定优先级。
- 一名玩家可采取临时措施为另一名玩家创造安全维修窗口。
- 两人可以完成主路径；三至四人可以并行处理、提高安全性或追求可选收益。

## 压力与风险来源

允许的压力来源内容池包括：

- 外部环境持续变化；
- 路线时间窗口；
- 电力、冷却状态和单一维护物资有限；
- 故障间的连锁反应；
- 舱外维修的暴露风险；
- 停靠补给带来的额外危险；
- 临时修复的延迟副作用。

MVP 只实现冷却故障链、单一维护物资、一次短促敌人干扰和风暴压力的代表用例。其他来源为后续内容池。所有压力必须服务玩家决策，禁止仅以高频随机故障制造忙乱。

## 差异化边界

- 主要目标不是进入独立设施搜刮后撤离，而是让共同机器持续运行并完成航程。
- 核心价值物不是单纯卖钱的废料，而是影响机器功能、路线与维修选择的零件和资源。
- 合作重点是诊断、调度、空间配合和连锁故障管理，而非共同攻击敌人。
- 巨构状态跨越整局并可视觉化，成为团队决策结果的持续记录。

## 成长方向

### 局内

- MVP 只实现一个团队共享应急旁路模块；
- 更多临时模块和路线能力在试玩后评审。

### 局外

- MVP 只实现一个永久故障预警中继；
- 个人等级、技能树、更多工具/模块和外观保留为后续候选。

成长优先增加选择，不以永久提高基础数值替代技能与协作。

## 内容扩展点

- 巨构功能模块；
- 工具、备件与临时修复方案；
- 故障类型与系统关系；
- 路线、环境灾害与停靠事件；
- 载荷、任务和可选目标；
- 不同巨构配置或底盘（远期）。

## 主要风险与控制

| 风险 | 控制方式 |
| --- | --- |
| 移动平台与联机物理复杂 | 首个原型使用静止舱段模拟运行，不立即移动整个关卡 |
| 故障退化为随机打地鼠 | 故障必须有原因、征兆、连锁关系与优先级选择 |
| UI 仪表取代 3D 劳动 | 诊断可使用仪表，但维修必须在空间中执行 |
| 系统数量迅速膨胀 | 原型只实现动力、冷却和一个舱外模块 |
| 玩家固定为无聊岗位 | 不锁职业，让工具和局势驱动临时分工 |
| 房主/权威端物理负担高 | 网络切片只同步一个共享任务物和一条故障链 |

## 首个灰盒原则

首个灰盒只验证第一人称移动、上下文交互、两种工具和一条冷却故障链是否清晰且值得重复。冻结范围与验收见 `GRAYBOX_SCOPE.md`。
