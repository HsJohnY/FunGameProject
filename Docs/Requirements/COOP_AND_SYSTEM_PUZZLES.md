# 多人协作与系统谜题需求

状态：需求基线 v1.0；具体事故内容按关卡阶段设计

## 1. 设计目标

协作围绕可理解的系统故障链展开，而不是独立密码小游戏或固定职业工位。玩家学习少量稳定规则，再在压力、空间和故障组合变化中应用这些规则。

- **COOP-01（已确认，MUST）**：主要协作由信息互补、空间操作和优先级协调三层构成。
- **COOP-02（已确认，MUST）**：谜题复用移动、工具、搬运、设备和环境规则，不为每个事故建立独立操作界面。
- **COOP-03（MUST）**：主线不存在强制四人同时操作的机关；两人可以完成，三至四人获得并行、容错和可选收益。
- **COOP-04（MUST）**：主要事故至少提供工具维修、搬运/安装、观察/调度、环境控制/防卫/救援四类贡献中的三类。
- **COOP-05（MUST）**：不得让一名玩家掌握全部信息并完成全部关键操作，使其他玩家长期围观。

## 2. 统一事故处理语法

所有主要事故复用以下认知顺序：

1. **发现异常**：通过声音、运动、泄漏、电弧、仪表或巨构状态识别症状；
2. **控制危险**：使用隔离阀、紧急断电、临时密封等直觉操作减缓恶化；
3. **定位原因**：沿编号、管线、电缆和系统关系找到根因；
4. **完成修复**：使用正确工具、部件和协作关系恢复系统；
5. **验证恢复**：从设备运动、声音、流体、电力和仪表确认结果。

- **PUZ-GRM-01（已确认，MUST）**：玩家无需先学习完整工程原理，必须能先执行一个明显有用且可撤销的控险动作。
- **PUZ-GRM-02（MUST）**：控制台报告症状和影响，不直接列出全部解题步骤。
- **PUZ-GRM-03（MUST）**：设备使用简短名称、稳定编号和可追踪的实体连接，关键信息可重复查看或标记。
- **PUZ-GRM-04（MUST）**：失败后指出未处理的主要因果链，队伍应能解释事故为什么恶化。

## 3. 三层协作

### 信息协作

不同位置可以呈现不同信息，例如外部裂口编号与控制室压力回路。信息必须简短、可复述、可标记；不使用大量随机符号、长序列记忆或仅靠颜色的编码。

### 空间与操作协作

玩家在不同位置完成有关联的动作，例如固定与紧固、抑制泄漏与更换管件、恢复供电与观察负载。短暂同步操作可用于高潮，但不能成为每次维修的常规门槛。

### 优先级协作

多个问题可以并存，但优秀执行原则上能处理全部主线问题。错误顺序带来可恢复的额外工作或短期恶化；少量可选奖励可能过期，不频繁制造必然牺牲。

## 4. 教学与认知成本

- **PUZ-LRN-01（已确认，MUST）**：新规则按照“安全单项教学—两个已知规则组合—加入一种压力变体”引入。
- **PUZ-LRN-02（MUST）**：一次教学段最多引入一个需要记忆的新核心规则。
- **PUZ-LRN-03（MUST）**：相同故障外观、声音和动作词在不同关卡保持相同含义。
- **PUZ-LRN-04（MUST）**：场景表现承担主要教学，HUD只补充目标、状态和失败原因。
- **PUZ-LRN-05（SHOULD）**：玩家首次接触规则时允许安全尝试；错误工具或可恢复误操作不造成永久损失。

明确避免：依赖长说明书、无提示穷举工具、同一外观改变规则、一次性密码锁、纯进度条协作，以及失败后仍无法理解原因。

## 5. 人数适配

| 人数 | 事故组织 |
| --- | --- |
| 2 人 | 缩短故障链、减少远距离并发；控制件可在操作后保持一段时间 |
| 3 人 | 两个主要工作面加一个可切换的机动职责 |
| 4 人 | 增加并行工作面、空间距离、短促干扰和可选目标，不增加强制工具种类 |

- **COOP-SCL-01（MUST）**：所有人数使用同一系统规则，不分别制作多套谜题答案。
- **COOP-SCL-02（MUST）**：缩放由事故配置显式控制，并可在自动测试中验证最小人数路径存在。
- **COOP-SCL-03（MUST）**：人数增加不简单延长维修时间、故障耐久或敌人生命值。

## 6. 世界观因果

巨构是用于维护气象稳定站的重型工程平台，并非普通交通工具。它超过设计寿命后被紧急重新启用，主体可靠但暴露子系统需要持续维护。风暴、沙尘、雷击、腐蚀和地形冲击产生可预期损伤；随着航程推进，校准核心与旧网络共振，部分异常逐渐显露为保护机制、旧指令冲突或前任维修队留下的封锁。

- **PUZ-LOR-01（已确认，MUST）**：故障必须来自设备状态、环境压力、超负荷运行或剧情系统干预，不使用无因高频随机损坏填充时间。
- **PUZ-LOR-02（MUST）**：相同基础故障随玩家修复和巨构升级逐步减少，新挑战主要来自已知规则的组合。
- **PUZ-LOR-03（MUST）**：重要修复留下功能、空间、外观、航线或剧情上的可见成果，避免“永远修不好”的挫败感。
- **PUZ-LOR-04（SHOULD）**：沿途环境预告主要风险，使玩家可以提前检查设备和准备工具。

## 7. 首个灰盒事故

首个代表场景采用冷却系统故障链：泄漏造成冷却液流失，水泵保护停机并因异物卡死，设备升温吸引一次短促干扰。玩家需要控漏、替换管件、恢复电力、解除卡死并确认温度回落。

该场景只验证三种工具的辨识、事故语法、搬运、信息沟通、2–4 人贡献和一次有限防卫，不追求正式美术或完整敌人阵容。

通过条件：

- 首次游玩的队伍能在不阅读长说明的情况下开始正确控险；
- 玩家能说出症状、原因、处理动作和恢复结果；
- 两人可完成主路径，四人无长期等待者；
- 玩家失败后能指出至少一个导致事故恶化的原因；
- 熟练队伍依靠沟通和规则理解提高表现，而不是记住隐藏脚本顺序。
