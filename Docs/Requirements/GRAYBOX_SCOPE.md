# 首个灰盒原型范围

状态：冻结 v1.0

## 1. 唯一目标

验证玩家能否在没有开发者口头解释的情况下，通过第一人称观察、两种明确工具、实体零件和一条短故障链，理解并享受“发现异常—控制危险—定位原因—完成修复—验证恢复”。

该灰盒不验证多人乐趣、正式内容量或美术品质。若维修劳动本身不清晰或不值得重复，应先修改核心操作，不进入网络切片。

- **GBX-GOAL-01（MUST）**：只回答“基础维修循环是否清晰、具有操作反馈并值得继续投入”。
- **GBX-GOAL-02（MUST）**：不能以联机沟通、敌人、成长奖励、剧情演出或正式美术掩盖基础循环问题。

## 2. 可玩范围

### 场景

- 一个静止但通过声音、轻量背景运动和低频环境反馈模拟行驶的冷却舱；
- 一条固定可达路线；
- 一个工具架、一个零件架、一台冷却泵、一个控制台、一处管道破裂点和一个任务物恢复点；
- Unity 基础几何、纯色材质、临时灯光和占位音效；
- 目标体验约 8–12 分钟，不通过固定等待补足时长。

### 玩家与输入

- 单人本地运行；
- 第一人称移动和观察；
- 上下文交互、工具主要功能、丢下/取消和最少必要菜单；
- 拾取、携带、放置、插入、设备操作和工具架换取；
- 一个主工具位和一个可见手持物位，无背包。

### 工具与物品

- 冲击扳手：松开、拆除、安装和紧固机械连接；
- 密封喷枪：通过连续覆盖临时控制泄漏；
- 一个实体替换管件；
- 工具无弹药和永久耐久，短时限制只提供反馈与节奏；
- 错误工具不消耗资源，并说明目标类型不匹配。

### 固定故障链

1. 控制台、声音和喷漏共同提示冷却压力下降；
2. 玩家找到破裂点并使用密封喷枪暂时控漏；
3. 冷却泵因压力异常保护停机，温度继续缓慢上升；
4. 玩家用冲击扳手松开损坏管件的机械连接；
5. 玩家搬运并安装替换管件，再完成紧固；
6. 玩家在控制台执行复位；
7. 泵重新运行，压力、温度、声音和设备运动共同确认恢复；
8. 成功后立即结算并允许重置，不继续等待下一事件。

### 失败与恢复

- 温度达到明确上限时失败；
- 失败说明未处理的主要故障阶段；
- 60 秒内可以重置并重新开始；
- 替换管件掉出场景时返回任务物恢复点；
- 不包含角色生命、倒地、死亡或战役损失。

## 3. 明确排除

首个灰盒不包含：

- 多人网络、房间、邀请码、聊天和标记；
- 线路桥接器与电气故障；
- 敌人、战斗、受伤、倒地和救援；
- 维护物资、支援物品、局内/局外成长；
- 随机故障位置、种子和事故导演；
- 巨构完整移动、载具物理和舱外区域；
- 战役存档、安全站和章节内容；
- 控制器、键位重绑定和完整设置菜单；
- 正式角色、工具精模、剧情配音、过场或正式视觉特效；
- 中继、云服务、第三方 Mod 或外部内容包。

排除项不得以“顺手实现”为理由进入。发现未来需要的接口时，只记录技术备注，不提前建设功能。

## 4. 最小工程边界

- **GBX-ENG-01（MUST）**：故障规则与 MonoBehaviour 生命周期分离，可在 EditMode 中推进和验证状态转换。
- **GBX-ENG-02（MUST）**：静态故障/工具定义与本次运行状态分离，不在 ScriptableObject 资产中保存运行时变化。
- **GBX-ENG-03（MUST）**：交互对象通过明确接口报告可用动作、条件和结果，不通过场景名称或全局查找耦合。
- **GBX-ENG-04（MUST）**：不提前建设通用服务容器、完整内容平台或网络抽象；只为当前灰盒建立可测试边界。
- **GBX-ENG-05（MUST）**：关键状态日志包含故障阶段、交互动作、目标 ID、失败原因和重置结果。

## 5. 交付物

- 一张可从编辑器和开发构建启动的冷却舱灰盒场景；
- 第一人称控制和上下文交互；
- 两种可区分工具和一个实体替换管件；
- 一条完整故障状态链、成功、失败和重置；
- 临时 UI、声音和可读反馈；
- EditMode 状态机测试；
- PlayMode 核心交互、任务物恢复和重置测试；
- 一份首次试玩清单和评审记录模板；
- 可重复的开发构建入口。

## 6. 工程验收

- 从干净启动进入场景后能够完整成功、失败并重置；
- 每个故障阶段具有至少两种互补反馈，不只依靠文字或进度条；
- 三次连续重置不会残留旧状态、重复订阅或丢失任务物；
- 错误工具、无效安装和任务物掉落均能恢复，不产生永久卡关；
- EditMode 与 PlayMode 约定测试全部通过；
- 开发构建无持续 Console 错误或未处理异常；
- 关键日志足以判断玩家在哪一阶段失败。

## 7. 玩法验收

至少邀请 3 名未阅读需求文档的玩家分别首次试玩，开发者不提供解题步骤，只帮助处理构建或输入故障。

通过条件：

- 至少 2 人能在一次会话内独立完成事故；
- 多数测试者能正确说出泄漏、泵停机、替换管件和系统恢复之间的因果；
- 多数测试者能从目标外形和动作词区分喷枪与扳手；
- 没有测试者因任务物丢失、目标不明或错误工具反馈而永久卡住；
- 至少 2 人认为核心操作值得进入双人协作验证，而不是只因未来内容设想愿意继续；
- 观察记录将事实、玩家原话和设计推断分开。

## 8. 退出条件

### 通过

工程与玩法验收均通过，可以建立双人网络切片分支。

### 有条件通过

因提示、数值或局部操作问题未通过，但维修因果和工具操作获得正面反馈：只修改灰盒并再次测试，不扩大范围。

### 不通过

多数测试者认为维修只是按提示走流程、工具缺乏手感，或无法理解事故因果：停止网络功能开发，重新评估工具动作或故障链。

只有明确记录评审结论后，才能改变本文件的冻结范围。
