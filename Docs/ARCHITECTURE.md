# 架构基线

当前只确立原则，不在玩法未知时预建复杂框架。

## 原则

- 玩法逻辑尽量使用普通 C# 类型，MonoBehaviour 负责 Unity 生命周期和场景适配。
- 配置与运行时状态分离；静态配置可使用 ScriptableObject，存档模型保持可序列化且可迁移。
- 模块通过明确接口或事件协作，避免全局可变单例成为默认方案。
- 第三方资源放入独立目录，通过适配层接入，便于升级或替换。
- 先为核心循环建立可测试边界，再扩展内容生产工具。

## 注释规范

- 项目自有业务代码默认使用中文注释；API、类型名、协议名和行业通用术语按需保留英文，避免生硬翻译降低准确性。
- 对公开类型、公共接口和重要入口使用 XML 文档注释，说明职责、输入输出和使用边界。
- 对状态转换、网络权限、时间顺序、数值依据和非直观 Unity API 写“为什么这样做”的行内注释。
- 不为显而易见的赋值、循环或语法逐行翻译；变量与方法名称本身应优先表达意图。
- 临时方案必须注明移除条件或对应阶段，不能只留下没有上下文的 `TODO`。
- 测试名称描述行为；测试注释只解释难以从 Arrange/Act/Assert 结构看出的场景。
- 注释与代码视为同一功能的一部分，行为改变时必须同步更新。

## 已确认产品边界

- 3D、固定第一人称；具体渲染管线在 M0 记录 ADR；
- 手工关卡骨架与数据化故障模块；MVP 不生成完整地图；
- Input System，键鼠优先，控制器在 MVP 前验证；
- 普通 C# 故障状态与 Unity 场景适配分离；
- 监听主机与中继目标在 M3 前进行技术选型；
- 存档只在安全站和结算边界写入；
- 非核心系统不得仅为未来扩展提前建设。
